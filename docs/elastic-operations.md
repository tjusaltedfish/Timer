# 弹性执行操作约定

所有修改继续通过 `POST /api/v1/operations`，由 `operation_id` 保证重试幂等，客户端先保存离线队列。任务完成必须由用户明确反馈。

| 操作 | 约定 |
|---|---|
| session.start | 新增 mode：keep_duration（默认）保留投入时长；keep_end 保留原结束时刻，原结束已过则拒绝 |
| session.extend | id、minutes（5–120）、occurred_at；running/paused 可增加时长；timer 导致的 awaiting_feedback 在实际操作时距计时结束不超过 30 分钟时可恢复 |
| waiting.snooze | id、check_at（含时区的未来时刻）、version（可选，客户端携带）；更新同一个未解决检查点，保留身份，版本从旧记录默认 1 开始递增 |
| feedback.create | interrupted 与 partial 都必须携带 remaining_minutes；都更新剩余工作量并提供规则重排入口 |
| settings.update | auto_adjust（默认 true）控制确定性小幅顺延；关闭后只生成待确认建议 |
| plan.apply / plan.undo | 复用有版本约束的原子应用/补偿撤销；blocked 提案不可应用，撤销不改变执行事实 |

续时只增加投入预算，不改写原始计划。暂停时续时仍保持暂停，恢复时才补上暂停经过的时间。计时结束后续时：以操作时刻重新打开区间并给予完整增加的时长；计时结束到续时之间的空档不计入实际投入。若离线续时实际发生在旧截止时刻之前，则撤回自动计时关闭的区间边界，按真实事件重建连续投入。

用户明确结束或已经提交反馈的执行段不能续时。另一段已在进行时，旧执行段不能重新打开。排程过期、任务结束、等待结果尚未解决时不能开始新执行。

后续顺延分两层：同日、后续弹性段、每段不超过 30 分钟且约束满足时可由确定性规则微调；其他变化需要提案确认。固定与保护时段、既有执行记录、截止与依赖都保留。离线先记录执行事实，后续安排以同步后的权威结果为准。

触发点为 session.start / session.extend / session.resume。检查点属于硬边界；任一后续块不能顺延时整条链均不移动。草稿有效期 15 分钟，按当前 revision 确认；自动应用后的撤销入口显示 10 秒，期间若日程有其他修改则服务端拒绝过期撤销。当前执行的预计占用也纳入新建与规则重排校验。

执行操作增加 defer_adjustment（默认 false）。客户端离线或已有排队操作时传 true：记录实际投入，但暂不自动替换未来块 ID，以免破坏同批后续操作引用。事件与服务器时刻相差超过 5 秒时也只建议；历史事件已经结束或需要改写过去时不会自动安排。session.adjustment 返回 none / applied / proposal / blocked，关联的提案保存在快照 proposals 中；轮询不会重复弹出同一提示。

本阶段证据：后台 52 项、Flutter 47 项测试通过，静态分析无问题，Windows 原生界面连接隔离后台完成一次顺延/撤销/等待改约闭环。真实手机通知与真实模型尚未验证。
